# Архитектурные решения (ADR)

Формат: контекст → решение → последствия. Новые решения добавляются в конец.

## ADR-001. Модульный монолит вместо микросервисов
**Контекст.** Старт продукта, одна команда, требования к согласованности (заказы, платежи, квоты).
**Решение.** Один NestJS-сервис с модулями по доменам и отдельный процесс worker из того же кода. Доменные сервисы собраны в один DI-контейнер (`DOMAIN_PROVIDERS`), чтобы избежать циклических зависимостей Nest-модулей; связи между доменами — через сервисы и hooks (`PaymentsService.registerHooks`).
**Последствия.** Простые транзакции и деплой. Масштабирование — репликами. Выделение сервиса (поиск, чат) потребует замены прямых вызовов на очередь/RPC — границы уже проведены по папкам.

## ADR-002. Drizzle ORM + SQL-миграции
**Решение.** Drizzle (типобезопасный SQL, генерация миграций, нет бинарного движка, как у Prisma). Миграции — SQL-файлы в репозитории, применяются отдельным шагом под advisory lock.
**Последствия.** Сложные запросы (поиск, аналитика) — через параметризованный `sql\`\``. При пересоздании колонок миграции проверяются вручную.

## ADR-003. Валидация zod-схемами из общего пакета
**Решение.** Входные схемы и контракты ответов — в `@lotok/shared`; backend валидирует ими же (`ZBody`/`ZQuery`), OpenAPI строится из `z.toJSONSchema`. Веб и мобильное приложение используют те же схемы и API-клиент.
**Последствия.** Одна точка изменения контрактов. Важно: в zod 4 `.partial()` сохраняет `default()` — для PATCH используется отдельный объект полей без значений по умолчанию (найдено интеграционным тестом).

## ADR-004. Два поисковых движка за одним интерфейсом
**Решение.** `SearchEngine`: OpenSearch (production; морфология, fuzziness, агрегации, гео) и PostgreSQL (FTS `russian` + `pg_trgm`). Индекс OpenSearch — производная проекция, обновляется заданиями `search.index`; сверка `search.reindex-stale` каждые 10 мин.
**Последствия.** Локальная разработка и CI без OpenSearch; интеграционные тесты прогоняются на обоих движках. Синонимы/транслитерация брендов — детерминированный словарь (`synonyms.ts`), `ё→е` нормализуется.

## ADR-005. Органика отделена от платного продвижения
**Решение.** Премиум — отдельный помеченный блок (до 3, ротация), выделение — визуальное, поднятие — изменение `bumped_at`. Платные услуги не участвуют в ранжировании релевантности.
**Последствия.** Прозрачность для пользователей и соответствие требованиям о маркировке платного размещения.

## ADR-006. Деньги — копейки и двойная запись
**Решение.** Все суммы — целые копейки. Каждое движение — проводка в ledger с ключом идемпотентности; счета пользовательских средств, выручки и бонусов разделены.
**Последствия.** Сверка `trial-balance`; возвраты — обратные проводки. Выплаты продавцам **не реализованы**: требуют провайдера с выплатами/сплитованием и договора (см. LEGAL.md).

## ADR-007. Платёжные провайдеры: mock + ЮKassa
**Решение.** Интерфейс `PaymentProvider`; mock-провайдер имитирует внешний сервис (своё состояние в Redis, страница подтверждения, HMAC-подписанные webhook). ЮKassa: создание платежа с `Idempotence-Key`, чек 54-ФЗ (позиции), webhook — проверка IP + повторный запрос статуса.
**Последствия.** Платёжный сценарий полностью проверяем тестами. Адаптер ЮKassa **не проверен на реальном магазине**. Онлайн-оплата не называется «безопасной сделкой».

## ADR-008. Аутентификация: короткий JWT + ротируемый refresh
**Решение.** Access JWT 15 мин (HS256) с `tv` (версия токенов) и `sid`; состояние пользователя кэшируется в Redis 60 с. Refresh — случайный токен, в БД только sha256, ротация при каждом обновлении, повтор старого токена (вне окна 30 с для параллельных вкладок) → отзыв сессии. Веб: httpOnly cookie + double-submit CSRF; мобильные: SecureStore.
**Последствия.** Мгновенная блокировка и «выход везде». Внешние провайдеры (VK ID, Яндекс ID, ЕСИА) подключаются через `external_identities`.

## ADR-009. Очереди BullMQ с inline-режимом для тестов
**Решение.** `JobsService` — фасад над BullMQ; `QUEUE_MODE=inline` выполняет обработчики в процессе (только тесты/отладка; запрещено в production валидацией конфигурации).
**Последствия.** Детерминированные интеграционные и E2E тесты.

## ADR-010. Реальное время: Socket.IO + Redis adapter/emitter
**Решение.** Socket.IO с комнатами `user:{id}`; события из любого процесса — через `@socket.io/redis-emitter`. Клиенты при переподключении досинхронизируют историю по REST; сообщения идемпотентны по `clientMessageId`.
**Последствия.** В production WebSocket проксирует nginx/ingress. Rewrites Next.js не проксируют upgrade — в dev/E2E веб подключается к API напрямую (`NEXT_PUBLIC_WS_URL`).

## ADR-011. Детерминированные рекомендации
**Решение.** Веса интересов по категориям с затуханием + свежие объявления + добор популярными. Без ML, без хранения сырых событий.
**Последствия.** Объяснимо, приватно (агрегаты, очистка пользователем). ML — следующий этап при наличии данных и правового основания.

## ADR-012. Отдельное приложение админ-панели
**Решение.** `apps/admin` — отдельный Next.js (свой хост, IP-allowlist на ingress, noindex). UI-кит пока скопирован из веба.
**Последствия.** Меньшая поверхность атаки публичного сайта. Технический долг: вынести UI-кит в `packages/ui`.

## ADR-013. Мобильные приложения на Expo
**Решение.** Expo SDK 54 (React Native 0.81, expo-router), общий `@lotok/shared`. Нативные сборки — EAS Build (`eas.json`).
**Последствия.** Один код для iOS/Android, OTA-обновления возможны. В CI проверяются типы, unit-тесты и экспорт JS-бандлов; нативные бинарники требуют EAS-аккаунта/Xcode/Android SDK.

## ADR-014. Хранилище файлов: S3 с публичным и приватным бакетом
**Решение.** Фото объявлений — публичный бакет за CDN (варианты WebP, immutable). Вложения чатов и документы — приватный бакет, выдача по подписанным ссылкам (S3 presign / HMAC для локального драйвера). Оригиналы удаляются после перекодирования.

## ADR-015. Ветки test → dev → main, одинаковый код во всех окружениях
**Контекст.** Нужна быстрая локальная проверка (Docker Compose) и production в Kubernetes.
**Решение.** Три долгоживущие ветки с продвижением только вперёд (`--ff-only`). Compose-файл и Helm-чарт живут в одном дереве; окружения различаются только файлами значений и секретами. CI — GitHub Actions: для `test`/`dev` — тесты и запуск стека в compose, для `main` — полный набор тестов, образы в ghcr.io, `helm upgrade --atomic` после ручного подтверждения (environment `production`). GitLab CI удалён — репозиторий на GitHub.
**Последствия.** В production попадает ровно проверенный код; нет конфликтов слияния из-за «разных конфигураций» веток. Образы web собираются с публичными адресами production (`NEXT_PUBLIC_*`), поэтому compose собирает свои образы локально.
